## 1. 这次重构的核心目标

本次任务不是在 10 天内成为资深 Java 工程师，也不是为了在项目里堆砌中间件，而是完成一个：

1. 能运行；
2. 能演示；
3. 能测试；
4. 能压测；
5. 能解释关键架构决策；
6. 能承接面试官连续追问；
7. 与个人气象、遥感和 AI 背景高度相关的 AI 全栈项目。

编码工作可以由 AI 辅助完成，但项目负责人必须理解：

- 系统解决了什么业务问题；
- 请求和数据如何在系统中流动；
- 每个模块为什么存在；
- 技术方案有哪些取舍；
- 系统在异常和并发情况下如何表现；
- 性能结论是如何测量出来的。

## 2. 项目业务定位

大禹系统是一个面向气象时空数据的可视化、检索和受控分发平台，主要完成三类工作：

1. 将气象模型和卫星数据生成的 WebP 产品叠加到 Cesium 三维地球上，展示实况和预报时间序列；
2. 允许科研用户按产品和时间检索、下载对应的 NetCDF 原始科学数据；
3. 对原始数据下载实施登录、用途登记、权限控制、安全校验、审计和管理员监控。

核心数据流：

```text
气象模型/卫星数据
    ↓
WebP 展示产品 + NetCDF 科学数据
    ↓
Cesium 浏览、时间轴播放、条件检索
    ↓
登录鉴权、用途登记、受控下载
    ↓
管理员统计、产品管理、数据新鲜度巡检
```

## 5. 关键架构原则

### 5.1 先兼容，再改进

第一版 Java 后端尽量兼容现有前端使用的 URL、请求参数、JSON 响应和状态码。必要时让 Spring Controller 暂时映射 `.php` 路径，避免同时重写前后端导致问题失控。

推荐接口迁移顺序：

1. `/api/products.php`；
2. `/api/files.php`；
3. `/api/fcst_latest.php`；
4. `/api/search.php`；
5. `/api/auth.php`；
6. `/api/download.php`；
7. 管理员接口。

### 5.2 先建立元数据索引，再谈缓存

当前公开文件接口会扫描和排序物理目录。真正的第一步不是直接引入 Redis，而是在数据发布阶段建立文件元数据索引，让用户查询数据库索引，不在每次请求中扫描文件系统。

建议新增 `data_files` 表：

```text
id
product_id
category
cycle_time
valid_time
file_type
relative_path
file_size
checksum
publish_status
created_at
updated_at
```

需要明确区分：

- 实况时间；
- 预报起报时间；
- 预报有效时间。

### 5.3 第一版继续使用 Session

当前系统是同源浏览器应用，第一版继续使用 Session、Cookie 和 CSRF。JWT 并非默认比 Session 更先进；只有在存在明确的跨端、跨服务或无状态认证需求时再引入。

### 5.4 下载控制流与数据流分离

Java 负责：

- 身份认证；
- 用途校验；
- 文件权限校验；
- 路径安全；
- 下载审计；
- 签发下载授权。

Nginx 或后续对象存储负责实际大文件传输。第一阶段优先考虑 `X-Accel-Redirect`，在确有对象存储和横向扩展需求时再引入 MinIO。

### 5.5 所有性能结论必须来自实测

不得在尚未压测时使用“QPS 8600+”“P99 12ms”“CPU 降低 90%”等数字。简历只记录实际完成、能够复现并有测试依据的成果。

## 8. 与 AI 协作的开发规范

### 8.1 标准工作循环

```text
确认业务目标
→ 分析现有实现和接口契约
→ 给出方案、备选方案及取舍
→ 设计接口和表结构
→ 小范围生成代码
→ 执行测试
→ 制造至少一个异常场景
→ 逐文件解释调用链
→ 项目负责人用自己的语言复述
→ 进入下一任务
```

### 8.2 不允许的做法

- 不让 AI 一次性生成整个系统；
- 不在不了解原因时接受大规模重构；
- 不通过删除测试来消除失败；
- 不因为代码能够编译就认为功能正确；
- 不把尚未运行的设计写成“已实现”；
- 不把尚未压测的目标数字写进简历；
- 不直接复制无法解释的面试话术；
- 不同时引入多个无法独立验证的中间件。

### 8.3 每个模块必须回答的问题

1. 一个请求从浏览器到数据库经过了哪些类？
2. Controller、Service、Repository 各自负责什么？
3. 数据存在哪里，谁是事实来源？
4. 两个并发请求同时进入会不会出错？
5. MySQL、Redis、文件系统或模型服务故障时会发生什么？
6. 哪些输入不可信，在哪里校验？
7. 为什么选择当前方案，而不是另一个方案？
8. 如何证明优化有效？
9. 流量增长十倍后最先出现的瓶颈是什么？
10. 删除某一层后会产生什么后果？

如果无法回答，先继续分析、调试和复盘，不立即进入下一模块。

- 数据库记录与物理文件如何保持一致；
- 重复发布如何保证幂等。

### 9.2 受控大文件下载

重点讲清：

- 为什么必须登录和记录用途；
- 如何阻止路径穿越和绕过门禁；
- 慢客户端为什么占用应用线程；
- 为什么拆分控制流和数据流；
- Java 流式下载、Nginx 内部转发和 MinIO 预签名 URL 的取舍；
- 服务端写完不等于客户端保存成功。

### 9.3 Redis 缓存与限流

重点讲清：

- 为什么缓存产品目录和最新批次；
- 数据库为什么仍是事实来源；
- 缓存何时失效；
- 缓存故障如何降级；
- 穿透、击穿和雪崩在本项目中的真实含义；
- 限流为什么不能只按 IP，特别是校园 NAT 环境。

### 9.4 AI 工具调用

重点讲清：

- 为什么不做普通聊天机器人；
- 自然语言如何转换成结构化时空条件；
- LLM 为什么不能直接查询数据库；
- Java 参数校验如何控制幻觉；
- Service 如何同时被 Controller 和 AI Tool 复用；
- 模型超时或不可用时如何降级。

## 10. 简历描述原则

简历不应写成“使用 Spring Boot 完成增删改查”，而要围绕真实问题、技术决策和验证结果展开。

建议最终聚焦：

1. 将请求时目录扫描重构为发布期文件元数据索引，降低气象文件检索中的磁盘元数据访问和排序开销；
2. 将受控下载的权限控制与大文件传输分离，结合 Nginx 内部转发降低 Java 业务线程占用；
3. 使用 Redis 缓存高频产品元数据，并实现明确的失效、降级和限流策略；
4. 将气象检索 Service 封装为 AI 工具，通过结构化输出把自然语言转换为确定性时空查询，并设置参数校验和故障降级；
5. 通过隔离压测记录优化前后的 P95/P99、吞吐量、错误率和资源使用情况。

只有在功能实际完成并有测试记录后，才能把对应内容改写成完成时态并写入正式简历。
