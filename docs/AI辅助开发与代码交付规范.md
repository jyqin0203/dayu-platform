# AI 辅助开发与代码交付规范

> 适用范围：`dayu-platform` 全仓库
>
> 文档状态：团队开发规范草案
> 制定目的：让 AI 将产品讨论、架构文档和用户自然语言意图稳定地转化为可理解、可验证、可接管的代码，避免一次生成大量无法审查的实现。

---

## 1. 核心目标

本项目允许并鼓励 AI 承担从需求理解到代码实现的大部分工程工作，但代码的架构边界、业务含义和验证结果必须能够被人理解和确认。

目标不是让用户预先设计每个类和每个方法，也不是让 AI 一次性生成完整系统，而是建立以下闭环：

```text
产品讨论和架构文档
+ 用户当前的自然语言意图
+ 仓库当前代码状态
        ↓
AI识别本轮真实目标和约束
        ↓
AI在既定架构内做常规实现决策
        ↓
AI完成一个可审查的代码闭环
        ↓
AI运行测试或命令验证
        ↓
AI解释“需求如何映射为代码”
        ↓
用户理解、验收或提出调整
        ↓
再进入下一闭环
```

衡量一次 AI 交付是否合格的标准不是“生成了多少代码”，而是：

- 是否符合已经确认的产品和架构设计；
- 是否只包含一个人能够理解的变更单元；
- 是否通过与本轮目标匹配的验证；
- 是否能清楚解释输入、行为、输出、依赖和限制；
- 用户能否在合理时间内接管这些代码。

---

## 2. 需求来源和优先级

AI 不得只根据用户最后一句话孤立生成代码。每轮任务的需求由三部分共同组成：

1. 仓库中的已确认文档和 `AGENTS.md`；
2. 此前已经达成一致的产品与架构决策；
3. 用户当前提出的自然语言目标或问题。

优先级：

```text
用户当前明确修正
> 已确认的架构和产品文档
> 当前代码中的既有契约
> AI自行推测
```

用户不一定能够一次完整、准确地表达技术需求。AI需要结合文档和代码理解用户真正希望实现的业务结果，但不得把重要的不确定性静默变成自己的产品决策。

示例：

```text
用户：“让用户能够查询已发布产品。”

AI应结合Catalog设计理解为：
- 只查询PUBLISHED产品；
- 返回产品摘要而非数据库实体；
- 按sortOrder排序；
- 不判断当前是否存在WebP/NC；
- 查询能力属于Catalog模块。
```

---

## 3. AI 与用户的决策边界

### 3.1 AI 可以自主决定

在不违反现有架构和业务决策时，AI可以自主决定：

- 类和内部方法的合理命名；
- 文件放入已确定模块的哪个层；
- 如何使用构造器注入既有接口；
- 内部私有方法如何拆分；
- 使用何种标准集合和 Java 语言特性；
- 为当前行为编写哪些单元测试；
- 如何运行编译、静态检查和测试；
- 添加哪些必要的 Javadoc 和解释性注释；
- 对不改变外部契约的小范围重构。

用户不需要提前逐个指定类名、文件名和每一行实现。

### 3.2 AI 必须暂停并请求确认

出现以下情况时，AI不能自行决定：

- 新增、删除或合并业务模块；
- 改变模块依赖方向；
- 修改已确认的产品行为；
- 修改权限、安全或隐私边界；
- 增加或删除数据库核心表、关系或关键字段；
- 改变公开 API 或跨模块接口语义；
- 引入新的中间件、框架或外部服务；
- 需求存在两种会产生明显不同用户结果的解释；
- 需要删除、覆盖或大规模改写用户已有代码；
- 预计变更超出单轮可审查规模；
- 测试失败且原因不能可靠定位；
- 需要提交、推送、部署或修改外部状态，但用户尚未授权。

### 3.3 用户表达不完整时

AI先结合文档和代码补全上下文，并用简短语言说明自己的理解。

如果补全部分只是既定架构内的常规实现细节，可以继续实施；如果涉及产品或架构选择，必须先确认。

## 4. 可审查的最小实现单元

### 4.1 基本原则

每轮只交付一个完整、可验证、可解释的闭环，通常是：

- 一个模块的一项业务能力；
- 一个明确的领域规则；
- 一个基础设施适配器；
- 一个 HTTP 接口及其业务调用；
- 一条跨模块用户故事的最小串联。

不允许使用“一次生成整个后端”“一次实现全部七个模块”等方式推进。

### 4.2 建议规模

以下是软限制，不是机械指标：

```text
单轮只涉及一个主要模块或一条垂直能力
生产代码新增尽量不超过250行
测试代码新增尽量不超过150行
新增核心概念尽量不超过5个
预计人工审查时间不超过30分钟
```

Java 的公开类型通常独立成文件，因此文件数不是唯一标准。重点是一次引入的概念数量和调用链长度。

预计超过限制时，AI必须主动拆分。例如：

```text
Catalog模块
├─ 第1轮：查询接口与DTO
├─ 第2轮：应用服务和Repository端口
├─ 第3轮：单元测试和异常规则
└─ 第4轮：数据库适配器
```

### 4.3 宽泛指令的处理

当用户提出“实现整个架构”等宽泛请求时，AI应：

1. 说明该任务无法作为单个可审查变更完成；
2. 根据依赖顺序拆分为若干闭环；
3. 选择最前面的一个闭环实施；
4. 完成、验证、解释后停止；
5. 等待用户验收后再进入下一项。

## 5. 每轮标准工作流

### 阶段 A：读取和定位

编码前必须：

1. 阅读仓库根目录 `AGENTS.md`；
2. 阅读本轮涉及的架构和模块文档；
3. 检查 `git status`；
4. 阅读将被修改的现有代码和测试；
5. 确认本轮属于哪个模块和哪条用户故事；
6. 确认不覆盖用户未提交修改。

### 阶段 B：简短实现说明

开始编码前，AI用简短语言说明：

```text
本轮要实现的业务结果
所属模块
明确不包含的内容
计划采用的验证方式
```

对于边界明确的常规任务，无需等待用户逐个批准文件即可实施。

示例：

> 本轮在 Catalog 模块实现“查询已发布产品”。查询只返回 PUBLISHED 产品并按 sortOrder 排序，不接入 Redis，也不实现管理员写操作。使用内存 Fake Repository 编写单元测试验证过滤、排序和空结果。

如果实施说明暴露出架构或产品分歧，则停止并等待确认。

### 阶段 C：小步编码

编码时必须：

- 遵守 package 和模块依赖边界；
- 只修改本轮必要文件；
- 使用构造器注入；
- 跨模块只调用公开 API；
- 不把数据库实体暴露为跨模块 DTO；
- 不硬编码凭据、生产路径和环境差异；
- 不顺便实现未要求的功能；
- 不进行无关格式化或批量重命名；
- 为公开契约和非显然逻辑添加必要注释。

### 阶段 D：自我验证

AI必须实际运行与本轮目标相匹配的验证，不能只阅读代码后声称正确。

验证失败时：

```text
定位原因
→ 修复代码或测试
→ 重新执行
→ 如无法可靠解决则停止并报告
```

禁止：

- 删除失败测试；
- 降低断言强度；
- 用 Mock 成功冒充真实集成成功；
- 在未执行命令时声称测试通过；
- 隐藏警告、失败或未覆盖场景。

### 阶段 E：交付说明

完成后必须按第 8 节格式汇报，并停止继续实现下一闭环，等待用户验收。

## 6. 注释和可读性规范

### 6.1 必须注释的内容

- 模块公开 Service 接口的职责和边界；
- 公开方法的业务语义；
- 输入参数中容易混淆的时间、状态和身份信息；
- 返回值的排序、分页、空结果和安全含义；
- 可能抛出的业务异常；
- 有副作用的行为；
- 领域不变量；
- 权限和安全边界；
- 为兼容旧系统而存在的非显然逻辑；
- 设计上“为什么这样做”的复杂代码。

推荐公共接口 Javadoc：

```java
/**
 * 查询近期可视化帧。
 *
 * @param query 产品、数据模式和UTC时间范围
 * @return 按有效时间正序排列的WebP帧；无数据时返回空列表
 * @throws ProductNotFoundException 产品不存在或未发布
 */
List<PreviewFrame> listPreviewFrames(PreviewQuery query);
```

### 6.2 不应添加的注释

禁止使用只重复代码字面含义的注释：

```java
// 返回产品编码
return productCode;
```

简单 record、getter、构造器和明显语句不需要逐行解释。注释应解释业务和原因，而不是翻译 Java 语法。

### 6.3 Mock 和临时代码

Mock、Stub 和临时适配器必须在类级注释中明确：

- 仅用于哪个 Profile 或测试；
- 不包含哪些生产行为；
- 不能复制到生产实现的部分；
- 未来由什么真实适配器替换。

---

## 7. 验证策略

验证方式根据变更类型选择：

| 变更类型 | 最低验证 |
| --- | --- |
| 值对象、领域规则 | 单元测试，包括正常值和边界值 |
| Service 业务能力 | 使用 Fake/Mock 端口的单元测试 |
| 模块依赖变化 | ArchUnit 测试 |
| Controller/API | HTTP 契约测试和参数校验测试 |
| MySQL Repository | Testcontainers 集成测试、迁移和索引验证 |
| Redis 缓存 | Redis 集成测试、命中/失效/降级测试 |
| 文件索引 | 临时目录样本测试、重复扫描和缺失文件测试 |
| 下载授权 | 权限、用途、路径逃逸和资产状态测试 |
| Nginx 下载 | 隔离环境端到端测试 |
| Copilot | 结构化输出、非法参数、超时和降级测试 |
| 多模块串联 | 用户故事或应用服务集成测试 |

验证报告必须包含：

- 实际执行的命令；
- 测试数量；
- 失败、错误和跳过数量；
- 每组测试证明的业务行为；
- 尚未覆盖的范围。

“编译通过”只能证明语法和类型关系成立，不能证明业务正确。

## 8. 每轮完成后的强制汇报格式

### 8.1 本轮目标

复述用户想实现的业务结果，并说明 AI 如何理解。

### 8.2 需求到代码的映射

说明：

```text
为什么属于当前模块
为什么创建或修改这些类
依赖通过什么方式注入
主调用链如何流转
```

### 8.3 文件变更清单

按新增、修改、删除分类列出文件，并用一句话说明每个文件的作用。

### 8.4 方法输入、行为和输出

至少覆盖本轮所有新增或改变的公开方法：

| 方法 | 输入 | 主要行为 | 输出 | 副作用/异常 |
| --- | --- | --- | --- | --- |
| `listPublishedProducts` | 无 | 过滤PUBLISHED并按sortOrder排序 | 产品摘要列表 | 只读 |

内部私有方法只解释具有重要业务规则的部分，不必逐个罗列。

### 8.5 依赖说明

说明：

- 注入了哪些接口；
- 为什么需要这些依赖；
- 是否新增第三方依赖；
- 是否改变模块依赖方向。

### 8.6 验证证据

```text
执行命令：
实际结果：
测试覆盖的行为：
```

禁止只写“测试通过”，不说明执行了什么。

### 8.7 限制和未实现内容

明确区分：

- 本轮已经完成；
- 使用 Mock 的部分；
- 尚未实现；
- 需要后续集成验证；
- 已知风险。

### 8.8 下一步建议

只建议一个最小下一闭环，不自动实施。

## 9. Git 和外部操作规范

- 编码前和完成后检查 `git status`；
- 保留用户已有修改；
- 不混入无关文件和格式化；
- 提交前检查 diff 和敏感信息；
- 未经用户明确要求，不执行 commit、push、建 PR 或部署；
- 不在生产服务器开发、安装依赖、运行迁移或压测；
- 不提交真实 HDF、NC、WebP、用户数据、凭据和生产配置。

如果用户要求提交，提交信息应描述本轮唯一闭环，不把多个未审查模块塞入同一提交。

---

## 10. 失败和停止条件

出现以下情况，本轮必须暂停并报告：

- 文档、代码和用户意图互相冲突；
- 无法判断正确的模块归属；
- 变更范围持续扩大；
- 需要突破依赖矩阵；
- 发现安全边界可能被削弱；
- 验证环境不可用；
- 同一失败连续修复仍无法通过；
- 必须依赖未确认的生产事实；
- 发现与本轮无关的用户修改会被覆盖。

暂停报告应包含：

```text
已经确认的事实
具体阻塞点
尝试过的安全检查或方案
需要用户决定的问题
```

## 11. 示例一：Hello World

用户意图：

```text
打印Hello World
```

AI自行完成常规实现判断：

```text
创建Java入口类
定义main方法
调用System.out.println
```

代码：

```java
public class Main {
    public static void main(String[] args) {
        System.out.println("Hello World");
    }
}
```

验证：

```text
执行：java Main
标准输出：Hello World
退出码：0
```

交付解释：

```text
JVM从main方法开始执行。
System.out.println将字符串写入标准输出。
实际运行结果与用户意图一致。
```

用户不需要提前指定类名、文件位置和 Java API，但 AI 必须解释并验证这些实现决策。

---

## 12. 示例二：Catalog 已发布产品查询

用户意图：

```text
实现查询所有已发布产品的能力。
```

AI结合架构文档确定：

```text
所属模块：Catalog
公开接口：catalog.api
业务实现：catalog.application
数据来源：Catalog自己的Repository端口
输出：ProductSummary，不暴露数据库Entity
规则：只返回PUBLISHED，按sortOrder排序
```

本轮合理范围：

```text
CatalogQueryService方法
Catalog应用服务
ProductRepository端口
Fake Repository
CatalogServiceTest
```

本轮不包含：

```text
MySQL
Redis
管理员写操作
Controller
其他模块
```

验证至少覆盖：

- 草稿和停用产品不会返回；
- 已发布产品按顺序返回；
- 没有产品时返回空列表；
- Repository 被作为依赖注入，而非在 Service 中直接创建。

完成后按第 8 节解释每个公开方法、依赖和测试结果，并停止等待用户验收。

## 13. 单个模块的推荐推进方式

一个模块不必一次完成。推荐顺序：

```text
第1轮：一个查询或命令的公开契约
→ 第2轮：对应领域规则
→ 第3轮：应用服务与出站端口
→ 第4轮：单元测试和边界测试
→ 第5轮：基础设施适配器
→ 第6轮：HTTP接口和契约测试
→ 第7轮：与依赖模块的小范围联调
```

每轮都必须形成“需求—代码—验证—解释”的独立闭环。不是所有简单能力都必须机械拆成七轮，但任何一轮都不能大到无法审查。

---

## 14. 合格交付的定义

一次 AI 代码交付只有同时满足以下条件才算完成：

- [ ] 目标来自已确认文档和本轮用户意图；
- [ ] 变更范围可在合理时间内审查；
- [ ] 没有引入未经确认的产品或架构决策；
- [ ] 代码位于正确模块和层；
- [ ] 公开契约有必要说明；
- [ ] 关键业务规则有测试；
- [ ] 实际执行了验证命令；
- [ ] 失败、限制和 Mock 范围如实报告；
- [ ] 完成后解释了输入、行为、输出和依赖；
- [ ] 没有自动进入下一模块；
- [ ] 没有未经授权提交、推送或部署；
- [ ] 用户能够理解并决定是否接受本轮代码。

如果代码能够运行，但用户无法理解它为何存在、如何工作以及如何证明正确，则交付仍然不合格。
