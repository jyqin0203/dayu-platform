# 候选索引验证结果：A/B/A与入库成本

用户确认后执行，日期2026-10-07。仅修改独立性能数据库，未改动`dayu_test:13306`、旧生产库或业务源代码。上一阶段的[原基线与方案](README.md)保留作为历史记录。

结论：**候选索引对带leadMinutes的历史NC检索有真实、可复现的局部收益，可以作为后续正式迁移候选；没有理由宣称全部查询大幅提速。** 当前仅492个NC，绝对延迟改善约1ms，业务上不是紧急瓶颈。本次实验后HTTP性能库已回撤至原索引，没有自动部署到测试或生产服务。

## 1. 最小改动和对照

唯一变更：

```sql
CREATE INDEX idx_assets_type_mode_status_lead_time
ON data_assets(asset_type, data_mode, status, lead_minutes, valid_time, id);
```

原索引、SQL、COUNT、字段、排序、分页和Redis策略均未改变。A/B/A使用同一9270资产/9762关联快照、同一JAR、同一CPU/内存限额、同一查询集/预热/次序种子。添加及移除索引前后资产和关联表CHECKSUM TABLE EXTENDED均一致。

| 阶段 | 状态 | 计时请求 |
|---|---|---:|
| A前 | 原索引，重新测3轮 | 54,000 |
| B | 只加候选索引，3轮 | 54,000 |

全部响应与快照独立计算的预期值逐字段一致，包括文件摘要、排序、页码、页大小和total；HTTP/内容校验错误均为0。测试数据没有扩充或复制成假大规模数据。

## 2. 效果：先看可归因的扫描量

目标场景：PRECIP、FORECAST、2026-09-02 06:00至09-08 06:00 UTC、leadMinutes=60、第1页、pageSize=20。

| 数据库指标（每请求/每语句） | A前 | B | A回撤 | A→B变化 |
|---|---:|---:|---:|---:|
| 列表SUM_ROWS_EXAMINED | 81 | 40 | 81 | -50.62% |
| COUNT SUM_ROWS_EXAMINED | 984 | 246 | 984 | **-75.00%** |
| 整个接口SELECT检查行数 | 1215 | 436 | 1215 | **-64.12%** |
| COUNT平均服务端时间，单并发 | 0.375ms | 0.236ms | 0.383ms | 约-37.0% |

计数来自真实HTTP请求的Performance Schema digest增量，不是用EXPLAIN估计行数替代实测。整个接口还包含产品可用性验证、全目录映射和产品关联读取。

B方案实际SQL计划：

- 列表命中新索引，访问20个匹配资产，再查20次产品关联；A方案需要访问61个资产以筛选出20个。
- COUNT命中新索引，使用覆盖索引读取123个匹配资产，再查123次产品关联；A方案从492个产品关联出发，查492次资产主键后过滤。
- 未使用FORCE INDEX或删除既有索引。计划见`results/ab-b-actual-sql-plans.json`，回撤计划见`results/ab-a-return-actual-sql-plans.json`。

## 3. HTTP指标：限定条件，不挑最好轮次

下表P95合并该场景3轮共3000条原始请求、按nearest-rank计算；吞吐为3000除以3轮累计耗时。三轮分项与所有场景见[完整A/B/A表](ab-table.md)及`results/ab-comparison.json`。

| 时效筛选 | A前 | B | A回撤 |
|---|---:|---:|---:|
| 单并发P95 | 2.14ms | 1.35ms | 1.94ms |
| 单并发吞吐 | 653请求/s | 761请求/s | 659请求/s |
| 4并发P95 | **6.67ms** | **5.61ms** | **6.64ms** |
| 4并发吞吐 | **865请求/s** | **1015请求/s** | **928请求/s** |

4并发相对A前：P95下降15.87%，吞吐提升17.40%；但相对A回撤，吞吐提升幅度更小，因此不把17.40%写成普适收益。原始三轮P95分别为A前6.70/6.77/6.61ms，B为5.67/4.82/5.65ms，A回撤6.52/6.50/6.69ms。回撤后扫描量和延迟恢复，支持该场景收益主要来自索引。

其他场景：扫描行数没有变化，延迟有调度/JIT噪声。例如预报长范围末页单并发P95从3.77到4.18再到3.01ms；不能声称所有查询都无回归或全部被优化。4并发末页仍受CPU配额节流影响，不将其时延变化归功于本索引。

这是本机HTTP、暖缓存、512MiB Java堆、128MiB DB buffer pool、两服务各100%CPU限额下的闭环试验，不是公网SLA、最大生产QPS或冷盘查询性能。NC文件约9.44GiB，但查询只读492条NC元数据，不读取9.44GiB科学内容。该批NC均属于同一RePPIC产品族，不能代表不同产品分布的大规模数据。

## 4. 空间和写入代价

新索引分配30个InnoDB页，即**491,520字节（480 KiB）**。data_assets索引总分配从5,095,424增到5,586,944字节。此处是索引页分配，不是备份大小或操作系统文件即时缩减量。

写入测试复用原生产JdbcAssetIndexStore及其事务逻辑，通过真实MariaDB回放同一9270条元数据/9762条关联；不模拟SQL返回。两种配置各预热一整轮，正式三轮交替B/A、A/B、B/A。

阶段：新增9270、无变化重复入库9270、固定10%子集元数据更新927、同子集缺失处理927（WebP删除索引、NC置MISSING）。每阶段校验资产/关联数、file_size总和、缺失状态。科学文件本身未被读取、复制、改名或删除。

最终逐轮表与结论见[入库成本表](ingest-table.md)，原始数据见`results/ingest-raw.json`及`results/ingest-summary.json`。该项只量化**扫描入库的数据库部分**，不包括目录遍历、文件stat、解析或完整批次检查；不能写成端到端扫描吞吐提升。

正式24个阶段全部完成且数据校验通过。新增9270条的三轮中位耗时A为19.518秒、B为18.954秒；无变化重复入库为19.729秒与18.779秒。更新和缺失处理的B中位耗时也未增加。在本次数据量和三轮回放下未观察到明显写入回归；这些小幅下降可能受缓存、调度等影响，不把它们解释为索引提升写入性能，也不推断更大数据规模下无成本。

收尾时查询实验库已撤销候选索引，9270条资产及其关联的校验和保持不变。临时性能服务已停止，旧线上三个服务的PID和启动时间未变化，常规测试实例四个服务仍在运行。元数据与独立写入实验库保留供复现。

## 5. 使用建议与交付边界

- 扫描行数下降明确、计划可解释、回撤可复现，候选索引值得保留为可选改进；当前小数据集并不迫切需要上线。
- 不需要修改业务SQL或Redis，不应同时加其他索引/改分页以混淆归因。
- 没有把候选索引写进正式Flyway迁移，也没有改动运行中的测试库或旧生产库；正式采用应另行走版本化迁移和上线验收。
- 保留所有原始轮次和较慢结果，不用试跑/热身与正式结果互相比“优化收益”。

[复现命令](optimization-reproduce.md)包含索引增删、A/B/A、真实仓储写入回放、资源限制和恢复方法；代码/环境摘要见`results/optimization-environment.json`。

## 6. 现在可使用的简历描述

> 针对气象平台历史NC时效筛选，在9270条真实资产索引（含492个NC）的隔离快照上设计联合索引，通过162000次A/B/A请求验证结果一致，将COUNT检查行数从984降至246（-75%）；限定4并发场景下P95由6.67ms降至5.61ms（约-16%），并验证索引空间和扫描入库成本。

这条描述是隔离环境验证结果，不写成“已上线生产”“百万级数据”或“全站性能提升”。如果需要更稳健的一行，可只保留75%检查行数下降和162000次正确性验证，省略微小绝对时延的百分比。

## 7. STAR面试讲法

- **S**：历史NC查询同时做分页列表和精确COUNT，真实文件容量较大，但实际只有492个NC资产。不能把文件字节量当作数据库检索规模。
- **T**：在不影响旧线上系统的前提下，找出一个可解释的瓶颈，并证明优化收益与写入代价。
- **A**：冻结真实元数据、单独部署受资源限制的Java/MariaDB；固定9种查询和1/4并发，分别拆解列表/COUNT。发现lead筛选缺少覆盖索引后仅加一个联合索引，做A/B/A三阶段，每阶段3轮；每次响应都与快照独立预期比对。再用生产仓储回放新增、重复和缺失处理，核对写入成本。
- **R**：COUNT检查行数984→246，撤回后恢复984；4并发P95为6.67→5.61→6.64ms，162000次请求无结果差异。新增索引480KiB。没有把其他场景的噪声当收益，也没有声称真实磁盘扫描或生产并发得到同等提升。
