# 现有 Redis 缓存效果评估（2026-10-08）

**结论：固定预报批次的帧列表缓存有效；当前前端的“最新预报批次”调用没有取得缓存收益。** 本轮仅评估，未新增或修改缓存方案、业务代码、线上配置或线上缓存。

## 三轮实测

主接口为前端 `loadTimeline` 实际调用的 `/api/files.php` **预报分支**，`number=200`。固定 4 个亮温产品 × 20 个真实起报批次，共 80 个查询，每个响应 12 帧；并发 4，每种条件每轮 800 请求。不是模拟 Redis/数据库，也不读取图片内容。这里“热点”指受控重复查询场景，未用线上访问日志证明流量热度。

下表是**三轮各自 P95/吞吐量的中位数**；完整三轮与每次请求记录见 [ROUNDS.md](ROUNDS.md) 和 `results/`。

| 条件 | P95 | 吞吐量 | 每轮 SELECT | 业务缓存命中率 |
|---|---:|---:|---:|---:|
| 关闭缓存 | 91.16 ms | 61.46 请求/秒 | 25,600 | 不适用 |
| 开启、空缓存首次请求 | 94.89 ms | 56.78 请求/秒 | 25,600 | 0% |
| 开启、预热后重复请求 | 18.98 ms | 477.08 请求/秒 | 800 | 100% |

预热后 P95 降低 **79.18%**、吞吐量约 **7.76 倍**，数据库查询由每请求 **32 次降至 1 次**（减少 96.875%）。收益来自复用帧列表与批次信息，省去重复资产查询及逐帧 NC 匹配。仍保留一次旧接口的产品/模式检查，所以不是零 SQL。首次请求没有减少 SQL，且增加 Redis 读取、序列化和写入开销。

补测前端 `/api/fcst_latest.php`：每轮每条件 200 请求、并发 4、相同 4 个产品 URL。开启缓存后的三轮业务命中均为 **0%**，SELECT 均未减少（800/轮）；P95 中位数 **41.23 → 59.92 ms**，吞吐量 **192.16 → 125.77 请求/秒**。原因是服务端每次把 `Instant.now()` 作为 `to`，而精确时间属于缓存键。相同 URL 实际产生不同内部查询键。实况帧列表也存在类似动态时间取键路径，本轮仅代码确认，未对其实测收益。

全部 **8,400 次计入统计的请求错误率为 0**；84 个查询的响应摘要跨缓存条件及轮次一致。100% 命中仅代表本次固定查询预热场景，不能写成线上整体命中率。

## 当前缓存覆盖与规则

| 能力/接口 | 缓存范围 | TTL |
|---|---|---:|
| `/api/v1/products`、`/api/products.php` | 已发布产品完整目录；单产品详情和管理查询不缓存 | 300 秒 |
| `/api/v1/preview-frames`、`/api/files.php`、旧 WebP 搜索分支 | WebP 帧列表，按产品、模式、起止时间、批次、时效、limit 分键 | 120 秒 |
| `/api/v1/forecast-cycles?assetType=WEBP`、旧最新批次/预报帧调用链 | WebP 批次列表，按产品及精确时间范围分键 | 120 秒 |
| NC 检索、NC 批次、下载候选、健康汇总 | 查询结果不缓存；其中引用的公共产品目录可独立命中 | — |

线上只读配置核对：缓存已开启，上述 TTL 与源码一致；Redis 连接/命令超时均为 250 ms。版本键 `generation` **没有 TTL**，本次观察 PTTL=-1；业务数据键实测约 119～120 秒，目录键约 300 秒。完整键格式、源码位置见 [CACHE-AUDIT.md](CACHE-AUDIT.md)。

- 文件扫描提交变更后发布 `AssetIndexChanged`，切换相关产品缓存版本；产品变更通过事务 `AFTER_COMMIT` 同时切换目录及该产品版本。
- 不遍历删除旧版本键：新请求改用新版本，旧数据等 TTL 自然过期。回填前检查版本，失效期间的旧结果不会成为新版本缓存。
- Redis 读写失败时回数据库；失败的失效操作在当前进程记为 pending，后续访问先重试切换版本，避免恢复后读旧值。损坏 JSON 会删除并回源修复。
- 这是事件失效＋TTL 的一致性措施，**不是强一致保证**。直接 SQL 写库不发事件、提交后进程中断、跨实例事件未传播等情况仍可能有旧值窗口；pending 标记仅在当前 JVM 内。没有因此新增方案。

## 失效和降级验证

在性能测量结束后，使用独立库与微型合成文件验证，详情见 `results/correctness.json`：

- 调用原扫描器真实入库，同一个已缓存查询立即从 **1 帧变为 2 帧**，版本改变；扫描及首次读取合计约 159 ms。这是微型功能场景，不是全量入库性能指标。
- 暂停独立 Redis 进程，保留旧缓存，并继续扫描新增第三帧。并发 4、12 次请求均返回 **HTTP 200 和最新 3 帧**，回退数据库成功；故障 P95 为 **1,561.95 ms**。250 ms 是单次 Redis 操作超时，不是整请求上限，同步版本读取、重试和排队会叠加。
- Redis 恢复后先完成失效重试，查询仍是 3 帧，随后恢复缓存命中，无旧结果重新出现。
- 实际调用事务型 `CatalogService.disableProduct`，提交后公开目录不再列出产品，原已缓存的 V1 预览请求返回 404。
- 注入损坏的测试缓存 JSON，接口回源正确并修复缓存。

## 条件、代价和限制

Intel Core Ultra 7 265K，20 逻辑 CPU、约 188 GiB 内存；共享服务器上的低优先级实验。原部署 jar SHA256 以 `12a7faae` 开头，Java 17、MariaDB 10.6.23；Redis 版本见环境记录。使用 **9,270 条真实资产元数据（8,778 WebP＋492 NC）、9,762 条关联、约 11.90 GiB 对应文件逻辑容量**；它们来自保留的真实快照，不能冒充当前线上全部数据。

隔离库端口 13309、Redis 16389、后端 18580/18581，均仅监听 127.0.0.1。两个后端分别开/关缓存，其余配置相同：每个 JVM 堆上限 384 MiB、Tomcat 8 线程、连接池 6；DB buffer pool 128 MiB，Redis maxmemory 64 MiB。CPU 亲和性：DB=2、后端=3、客户端=4、Redis=5，nice=15。未压测正式 HTTP 服务、未清正式 Redis、未启动自动扫描或 AI。

预热 80 个查询后共有 164 个 Discovery 键，键内存约 **306 KiB**，Redis `used_memory` 约 **1.31 MiB**。缓存需要 JSON 序列化、网络访问和内存；旧版本数据留存到 TTL，动态时间键还会增加无效填充。Redis 故障保持可用，但延迟及数据库负载明显上升，且当前没有统一熔断跳过全部 Redis 尝试。

首次请求仅指 Redis 空缓存，不是 JVM/数据库冷启动。冷请求按 10 个区块测试，每区块开始前仅清空独立 Redis，再访问 80 个不同键一次；重置和预热不计入请求时间。三种条件均用相同查询序列、并发和请求数，吞吐量分母为区块执行时间之和。两 JVM 先用相同请求预热；各轮顺序及原始数据均保留。命中率统计业务 payload，不把 generation GET 的命中误当业务命中。JDBC 计数不含驱动 Ping/事务协议。两版均有同样的计数探针开销；结果是本机受控测试，非生产 SLA，也未测缓存击穿、长期流量和多实例一致性。
