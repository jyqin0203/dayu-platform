## 代码发现与待证实瓶颈

`PersistentAssetScanner` 已预加载产品目录并缓存产品家族映射。普通文件调用 `JdbcAssetIndexStore.upsert`：单文件事务内按路径查资产，查关联产品；即使无变化仍 UPDATE last_seen_at。正常已存在文件对应 2 次 SELECT + 1 次 UPDATE，另有事务开销。这是静态调用链结论，不是实测 SQL 次数；批次、清理和任务记录还有额外 SQL。

因此值得下一步测数据库往返/事务提交，但不能用本轮约 0.23～0.31 秒的目录阶段与另一次不同条件的数据库实验拼接，宣称数据库占比。当前不能确定是否值得实施优化。

若真实数据库基线证实该瓶颈，最小候选是**有界分块读取资产及关联、比较差异、批量标记无变化文件已见**；新增/变化可先沿用现有写入逻辑。避免一次加载全部历史索引导致内存随历史规模无界增长。仍遍历全根，不以最新日期过滤，保留历史回补和覆盖检测。必须保持大小写路径冲突校验、微秒时间比较、关联变化检查、RePPIC 三文件事务及数据库历史周期合并，以及根扫描失败不清理。不能直接省略 last_seen_at 更新导致无变化文件被误删。
