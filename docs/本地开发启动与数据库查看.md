# 本地开发启动与数据库查看

本配置只连接本机的独立开发数据库，不使用生产目录、生产数据库或其他项目的容器。

首次 clone、生成配置与构建请先看 [新电脑首次启动指南](新电脑首次启动指南.md)。以下连接信息对应默认 `dayu-local` 实例；使用自定义端口时，以 `.env.local` 为准。

## 连接数据库

在你使用的数据库管理工具中，新建 MariaDB 连接：

| 配置 | 值 |
| --- | --- |
| 主机 | `127.0.0.1` |
| 端口 | `13306` |
| 数据库 | `dayu` |
| 用户名 | `dayu` |
| 密码 | 项目根目录 `.env.local-db` 中的 `DAYU_LOCAL_DB_PASSWORD` 值 |

`.env.local-db` 已被 Git 忽略，不提交、不分享。它与存放 Qwen 配置的 `.env` 分开；Docker 只接收数据库配置。新的启动脚本会按白名单把 Qwen 配置传给 Java，不把模型密钥传入数据库容器，详见 [配置与图片接入](后端配置与图片资源接入.md)。

JDBC 地址：`jdbc:mariadb://127.0.0.1:13306/dayu`。

## 后端入口

浏览器打开 <http://127.0.0.1:18080/api/v1/products>。没有产品时应返回 `[]`，这是正常结果，不是系统未启动。

这只是后端 HTTP 服务，首页不是已完成的前端地图页面。首次初始化关闭自动扫描、Redis 缓存和 Copilot，没有导入样本。新启动脚本的 Copilot 开关改由 `.env` 控制；启动本身不调用模型。产品目录与本地管理员已完成下面记录的初始化。

## 先看哪些表

| 表 | 用途 |
| --- | --- |
| `products` | 产品目录 |
| `product_mode_policies` | 每个产品的实时/预报模式策略 |
| `product_admin_events` | 产品管理操作记录 |
| `data_assets` | NC/WebP 文件的索引，不存文件内容 |
| `data_asset_products` | 文件与产品的关联 |
| `asset_scan_runs`、`asset_scan_errors` | 扫描批次和错误 |
| `users`、`login_attempts` | 用户与登录尝试 |
| `download_events`、`download_event_products` | 下载授权审计及产品快照 |
| `flyway_schema_history` | 建表脚本执行历史，不是业务数据 |

首次启动由 Flyway 执行 V1～V4 迁移，首次建表后业务表为空是正常的。2026-10-03 已通过业务接口初始化产品目录，尚未扫描文件，因此资产表仍为空。

可以先执行只读 SQL：

```sql
SHOW TABLES;
SELECT version, description, success FROM flyway_schema_history ORDER BY installed_rank;

SELECT id, asset_type, file_name, status FROM data_assets LIMIT 20;
```

## 再次启动与停止

启动前打开 Docker Desktop，在项目根目录运行：

```powershell
.\scripts\start-local.ps1
```

脚本复用已构建的 JAR，不编译、不跑测试；后端在后台运行，只监听本机 `18080`，日志在忽略 Git 的 `logs/` 中。若 `18080` 已被占用会停止启动流程，不杀其他进程。

新脚本启动的后端可以执行 `scripts/stop-local.ps1` 安全停止，加 `-Database` 同时停止本实例数据库并保留数据。旧脚本启动、没有进程记录的后端，需要在任务管理器中根据已核实 PID 停止，不要结束所有 Java 进程。默认实例也可单独停止数据库：

```powershell
docker compose --project-name dayu-local --env-file .env.local-db -f infra/compose.local.yml stop
```

数据库持久化在命名卷 `dayu-platform-mariadb-local-data`，停止/重启容器不清空数据。**不要执行 `down -v`、删除此卷，或以为修改密码文件就能重置已有数据库密码。** 修改数据库密码需要单独操作并同步本地配置。

以后修改 Java 代码，需要重新构建 JAR、停止旧后端再启动；本脚本不会自动构建或热更新。

## 已完成的产品初始化（2026-10-03）

来源是旧仓库 `database/migrations/002_product_management.sql`、`003_reppic_products.sql`、服务器只读调查记录和已确认的产品族映射，没有直接执行旧 SQL。配置清单在 `infra/local-products.json`。首次初始化遗漏了线上 CTH/CER/COT 预报模式，已于 2026-10-03 经用户确认，通过管理员接口补齐；不能以初始化 SQL 代替线上实际配置。

| 产品范围 | 数量 | 已配置模式 | 当前状态 |
| --- | --- | --- | --- |
| RGB、FRGB | 2 | REALTIME | PUBLISHED |
| CLP、CBH、CWP | 3 | REALTIME | PUBLISHED |
| CTH、CER、COT | 3 | REALTIME、FORECAST | PUBLISHED |
| BT625、BT695、BT742、BT855、BT108、BT120、BT133 | 7 | REALTIME、FORECAST | PUBLISHED |
| PLP、PRECIP | 2 | REALTIME、FORECAST | DRAFT：用户确认暂无必要色标 |

合计 17 个产品、29 条启用模式策略（17 个 REALTIME、12 个 FORECAST）；公开接口返回 15 个产品。模式配置成功不代表该产品已发布，更不代表已有文件。三种云预报的依据是服务器调查记录第 121 行的 active 状态，不是仅凭旧前端注释；其他云预报暂未启用。没有为了发布降水而取消 `colorbarRequired`。

新鲜度阈值沿用旧配置：非降水实况 90 分钟、BT 预报 360 分钟、降水实况 120 分钟、降水预报 180 分钟；这是健康判断阈值，不是扫描频率。

CTH/CER/COT 的线上阈值未在调查记录中给出，本地暂取 360 分钟，后续按实际更新频率调整，不冒充线上原值。`stale_after_minutes` 表示数据陈旧告警阈值：实况按最新有效时间 `validTime`，预报按最新起报时间 `cycleTime` 判断；距现在超过阈值时标记 STALE。它不是预报时效、缓存 TTL、文件删除期限，也不会单独禁止查看或下载。没有任何数据时是 MISSING，而不是 STALE。

本地应用管理员账号为 `local-admin@dayu.test`；随机密码存放于被 Git 忽略的 `.env.local-admin`。它不同于数据库的 `dayu` 账号。首次初始化先走注册接口，在空用户库中将这一名用户引导为 ADMIN，然后重新登录；只有这一步使用了受控本地 SQL，产品/模式/发布全部走带 Session 和 CSRF 的管理员接口。

执行入口：`scripts/initialize-local-products.ps1`。只有首次空库初始化使用 `-BootstrapAdmin`；以后运行不带此参数。重复运行跳过已存在的产品，不覆盖用户改动，也不自动修复中途中断的配置。

首次初始化核验：数据库 17 个 CREATE、26 个模式 UPDATE、15 个 PUBLISH，共 58 条产品管理审计。补齐云预报后新增 3 个 UPDATE，总计 61 条；资产数和扫描任务数仍均为 0。没有运行全量测试、调用模型或操作生产环境。

查看具体模式与阈值：

```sql
SELECT p.code, p.status, m.data_mode, m.enabled, m.stale_after_minutes
FROM products p
JOIN product_mode_policies m ON m.product_id = p.id
ORDER BY p.sort_order, m.data_mode;
```
